# Pending release-note items

2.63.0's release notes, for the `AmplifyCognitoClient` beta and the Auth plugin changes that shipped with it, are in its [GitHub release](https://github.com/aws-amplify/amplify-swift/releases/tag/2.63.0).

Customer-visible changes since 2.63.0, for the release notes of the release that first ships them. Each entry names
the change and who sees it, and links to more detail where there is some. "2.63.0" in a row means that release's
behaviour.

## Cognito Auth plugin

| Change | Who sees it | Details |
|---|---|---|
| Security: the sign-in's verbose lines no longer print the challenge session. The challenge a sign-in answers (the engine's `RespondToAuthChallenge`) had no description of its own, so every verbose line that printed it by reflection showed its session in full, and the username: the "Sending event" lines of the sign-in actions when Cognito answers with a challenge (SRP, custom auth, `USER_AUTH`, migrate auth, auto sign-in after sign-up, and each `confirmSignIn` answer), and the lines that print a sign-in state holding one. It now prints with the session as `<REDACTED>` and its two usernames masked (`alice` as `al*ce`), as the sign-in data already did, in `print`, `debugPrint`, interpolation and `dump`. The other fields print as they did nested in an event or state in 2.63.0; `parameters`, Cognito's challenge parameters, still print in full, and can hold a username (`USERNAME` on a custom challenge). Printed on its own, the challenge now names its type in full (`InternalAWSCognitoAuth.RespondToAuthChallenge(…)`). The one app-visible text that prints it is the `AuthError.unknown` an MFA setup throws when it offers only SMS, which the plugin does not set up: "Unable to determine next step from challenge:" and the challenge, which held the session and username in full in 2.63.0 | Anyone reading or collecting verbose logs; apps that log or show the text of `AuthError.unknown` from `signIn` or `confirmSignIn` | — |
| Fix: `confirmSignIn` now throws when the user pool accepts the answer but the identity pool step after it fails (`GetId` or `GetCredentialsForIdentity`), with the identity pool's error, as `signIn` does (for example `AuthError.service` with `AWSCognitoAuthError.invalidParameter`), and logs the verbose line `Authorization reached an error state …` that `signIn` logs there. In 2.63.0 it never returned, and every Auth call queued behind it waited too | Apps with an identity pool that sign in with a challenge (MFA, a new password, custom auth, a factor selection) | — |
| Upgrading from the AWS Mobile SDK (AWSMobileClient, Amplify v1): a signed-out record (`{"noCredentials":{}}`) in the plugin's saved session now stops the migration, as a login does: nothing migrates over it, the old keychain locations are cleared, and the plugin logs the info line `A signed-out session already exists, discarding legacy credentials`. In 2.63.0 the migration read that record as no session, so an old AWSMobileClient login migrated over it and signed the user back in. A sign-out through `AmplifyCognitoClient`'s default session saves that record, and so, with a keychain access group set, does the plugin's own sign-out (the access-group row below). Without an access group the plugin's sign-out deletes the record, so an app that uses only the plugin without one is not affected; with one, the plugin's sign-out already clears the old keychain locations, so only an old login that survived that clear, or was saved there since, is now dropped instead of migrated. A guest is still not a login: a guest saved over the signed-out record (by the plugin, an app extension or the client) lets an old login migrate over it again | Apps upgraded from AWSMobileClient or Amplify v1 that use `AmplifyCognitoClient`'s default session or a keychain access group, or roll back or forward between a client build and a plugin build | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.8 |
| Behaviour change: with a keychain access group set, ending a login through the plugin (`signOut`, local or global; `clearFederationToIdentityPool`; the sign-out after `deleteUser`) now saves the signed-out record, `{"noCredentials":{}}`, in the shared keychain service instead of deleting the session record: when the record holds a login (user pool tokens or a federated identity), or is already signed out. A guest's sign-out still deletes the guest's record, as does a sign-out over a record the plugin cannot read, and a sign-out with nothing saved writes nothing, so neither stops a login's migration. Those are the bytes `AmplifyCognitoClient`'s default session saves when it signs a session out, and every plugin release reads them as signed out (releases back to 2.10.0 decode them as `AmplifyCredentials.noCredentials`, the value for no saved session). The next sign-in replaces the record. The record then stops an app extension's first access-group migration (`migrateKeychainItems: true`), as a login does, so a stale login in the extension's own keychain is never moved in over a user who signed out; in 2.63.0 only a device record left by a user-pool sign-in stopped it. An extension's first access-group transition without migration counts the record too, as it counts a login, and keeps the extension's own old keychain items instead of clearing them. The AWSMobileClient (Amplify v1) migration treats the record as a signed-out session (the row above): it migrates nothing over it and clears the old locations, which the sign-out already clears, until a guest replaces the record; a guest `AmplifyCognitoClient`'s default session fetches over it clears those logins first, best effort. A plugin sign-out after a configuration change that copied the login now survives a rollback to the build with the earlier configuration, whose rule copies the signed-out record over the earlier copy, as after a sign-out through the client. Without an access group nothing changes: the record is deleted. `AmplifyCognitoClient.storedSessions(…, includingSignedOut: true)` in that access group now lists `.default` as a signed-out row after a plugin sign-out of a login (with no label or username unless the client saved them beside the record), where it listed no `.default` row; the default listing is unchanged. Logs under an access group: such a sign-out logs the keychain store's verbose `[KeychainStore]` lines for setting an item in place of those for removing one, and at the next launch the plugin no longer logs the info line `No existing session found.`, and its verbose credential-store line sends `completedOperation` with no credentials where it sent `throwError(itemNotFound)` | Apps with a keychain access group, especially with app extensions; apps that list stored sessions with `includingSignedOut: true` | [Decisions](auth-client-DECISIONS.md), decision 40 |
| One new log line of the `InternalAWSCognitoAuth/<File>.swift` form, the info line above in `MigrateLegacyCredentialStore`, so the state-machine actions' `\(#fileID)` sites go from 254 to 255, in 66 files | Anyone filtering or parsing plugin logs by file prefix | — |

## AmplifyCognitoClient (`@_spi(AmplifyExperimental)`, beta)

| Change | Details |
|---|---|
| Security: the engine's verbose lines no longer print a sign-in challenge's session: a sent challenge answer (`initiateTOTPSetup`, say) shows it as `<REDACTED>`, beside the usernames the client already redacted. In 2.63.0 it was printed in full | — |
| A Cognito internal error (`InternalErrorException`, from either pool) and an error status the SDK does not model are `AuthClientError.service` with no code in every call: `USER_AUTH`, auto, device SRP and passkey sign-ins, `deleteUser`, a sign-out's revoke and global sign-out, and the passkey credential calls included. In 2.63.0 they were `AuthClientError.unknown`, and an internal error in those calls and sign-ins still suggested reporting a bug. A 5xx or an internal error suggests a retry, and any other status says the service refused the request with an error the client does not recognise (the description has the status and message). In a `.partial` sign-out, the revoke's or global sign-out's suggestion says instead that it will not be retried; the global sign-out's says the user's other sessions stay signed in, without the "unless the request reached the service" that only a transport failure's has. Code that matched `.unknown` for these must match `.service(nil, …)`. The credentials providers report both cases the same way, so a provider's `CredentialsError` and its `disposition` don't change. The Auth plugin keeps `AuthError.unknown` | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Errors" |
| A refresh, a sign-out's revoke and the passkey credential calls report a transport failure as every other call does: a response that is not JSON, or a bad server response, is `.service` with no code, "The service returned a response that could not be read." and a retry suggestion; a network failure has the network texts, with the network error underneath; any other URL loading failure is "The service request failed.". In 2.63.0 an unreadable body on a refresh kept the engine's text, a passkey call that failed offline said "This should not happen", and an unreadable revoke had an empty description. In a `.partial` sign-out, the revoke's and global sign-out's suggestion says instead that it will not be retried | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Errors" |
| A sign-out that can't finish, because the saved record kept changing (`.failed(.storageUnavailable(.interrupted))`) or became unreadable (`.failed(.unknown)`), carries the first server-side failure as its underlying error, the global sign-out's first, mapped as any other call maps it, with the network or retry suggestion. In 2.63.0, after a failed global sign-out, it carried the empty placeholder `revokeTokenError` of a revoke that was never sent, and a revoke that failed on the network said there that the session was signed out on this device and the revoke would not be retried, though the session was still signed in. A sign-in that reaches a challenge as a sign-out, purge or user deletion ends the session throws the sign-in-cancelled `.invalidState`, where it could return the challenge the sign-out had ended | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Errors" |
| A refresh token refused as reused a second time, at least 30 seconds after the first, with nothing saved meanwhile, still expires the session, forced or not. Its `sessionExpired` now says the refresh token was already used and no refreshed tokens were saved, so the session can't be renewed, with `refreshTokenReused` underneath, where 2.63.0 gave the "has expired or been revoked" text of a refused token with `refreshTokenInvalid`. The expiry now holds while the saved login keeps the refresh token proved dead, so another writer saving the same login again, before or after the expiry, no longer clears it: the same credentials in other bytes (the Auth plugin over `.default`, an app extension over a named session), or the plugin's save of them with its expired flag set. In 2.63.0 the next call refreshed the dead token again, and a later refusal sent a second `.sessionExpired`. A login with another refresh token ends the expiry. The expiry lasts while the session is in memory: until every handle and provider for it is released, or a relaunch | [`issues/rollback-behaviours.md`](issues/rollback-behaviours.md) §3 |
| A federated session's errors name what works on it. When the identity pool no longer accepts its provider token, its `sessionExpired` says so ("Session "<id>"'s provider token is no longer accepted by the identity pool.") and suggests calling `federateToIdentityPool` with a new provider token, where it said the refresh token had expired or been revoked and suggested signing in, which the client refuses on a federated session; the underlying error is unchanged. Its signed-in operations' `notSignedIn`, and `fetchAuthSession`'s `userSubResult` and `userPoolTokensResult`, say the session has no user pool user ("Session "<id>" has no user pool user: it is federated to the identity pool."); they, `getCurrentUser`'s `notSignedIn` and the token provider's `notConfigured` suggest calling `clearFederationToIdentityPool()` or signing the session out before signing in through the user pool. Of the `notSignedIn` texts, only a signed-out session's AWS credentials still say that a signed-out session never falls back to guest credentials | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Federation to the identity pool" |
| WebAuthn: a `"WEB_AUTHN"` answer to a first-factor selection that does not offer it is refused with `.validation(field: "challengeResponse")` before anything is sent, on every platform, and the selection stays pending. 2.63.0 accepted it from a fixed list on every OS, and Cognito's WebAuthn challenge then ended the sign-in. The Auth plugin refuses it only below iOS 17.4 and macOS 13.5 and on tvOS and watchOS | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Sign-in steps and confirmSignIn" |
| `confirmSignIn` after a TOTP setup whose last request failed with a step (`.resetPassword`, `.confirmSignUp`) throws `.invalidState` ("Cannot use confirmSignIn in the current state. Call signIn to start the sign-in again.") and ends the attempt, as the Auth plugin refuses it, where it never returned and held the session's sign-ins until a sign-out | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Sign-in steps and confirmSignIn" |
| A refresh of a carried session that is waiting for its identity, whose save loses to another process's sign-out, answers as signed out: `fetchAuthSession`'s fields and both providers fail with `notSignedIn`, whose disposition is `.discard`. In 2.63.0 every field failed with `sessionExpired`, and the providers with the identity step's error (`CredentialsError.notConfigured` for a known refusal, else `.unknown`) | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Changing the configuration" |
| A `.default` login copied from a configuration with an identity pool, after that identity pool is removed, refreshes only when its user pool tokens need it, whatever AWS credentials it kept. In 2.63.0, once those had expired, every token request, signed-in operation and `fetchAuthSession` refreshed it and rewrote the record | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Changing the configuration" |
| AWSMobileClient (Amplify v1) logins: a `.default` sign-out or purge clears them before it writes the signed-out login or deletes the login, so a failed write or delete, or an app stopped right after it, leaves none for a plugin build to migrate back. 2.63.0 cleared them after. `fetchAuthSession()` on `.default` that saves a guest over a signed-out record clears them again first, best effort, so a login a sign-out failed to clear is not migrated back once the guest replaces the signed-out record; not over an absent record, nor over a label set before anyone signed in (an app that never signed in through the client keeps them for the plugin to migrate), and never for a named session. **Rollback:** plugin releases before 2.63.0 migrate those logins over whatever `.default` holds, with no check; 2.63.0 keeps a user signed in through the client, but migrates over a guest and over a signed-out `.default`; later releases also keep a signed-out `.default`, until a guest replaces it (the Auth plugin row above) | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Rolling back and forward" |
| A hosted-UI sign-out whose logout page is closed (by the user, `cancelWebUISignIn()` or `resetSystemSheet()`) on a `.default` session the Auth plugin saved as expired returns `.failed(.userCancelled)` and keeps the session, where 2.63.0 signed it out on the plugin's saved flag (`.complete`, or `.partial` with no `hostedUIError`). On a session a refresh found expired while it was in memory (until every handle and provider for it is released, or a relaunch), a closed page still signs out on this device, with `.partial`'s `hostedUIError` `.userCancelled`, but only while the login being signed out still has the refresh token found dead: a new login another app in the access group saved since is kept, `.failed(.userCancelled)`, where 2.63.0 revoked it and signed it out | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Hosted-UI sign-out" |
| `cancelWebUISignIn()`: a cancelled passkey call throws `.userCancelled` once it has released the system sheet, as a hosted-UI sign-in does, so `systemSheetHolder` no longer names the session by then, where 2.63.0 answered while the sheet was still closing and an immediate retry got `browserBusy`. If the sheet isn't released within a second, the call throws anyway, and the sheet stays held until the passkey ceremony finishes | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Cancelling and recovering" |
| Hosted UI: a second hosted-UI sign-in on a session whose first is still queued behind another session's sheet throws `browserBusy(holder:)` naming the session that holds the sheet ("Session "work" is already waiting for the system sheet, which session "home" holds."), where it named itself. One whose first is in progress but neither holds nor waits for the sheet (before it asks, or committing after) says "Session "work" already has a hosted-UI sign-in in progress.", adding ", and session "home" holds the system sheet" when another session holds it; `holder` is then that session, or the session itself. A sign-out, purge or user deletion that lands just as a hosted-UI attempt begins makes that sign-in throw the sign-in-cancelled `.invalidState` ("The sign-in was cancelled: the session was signed out, purged or deleted while it was in progress."), as one landing at any other point does, where it threw `.userCancelled`. A hosted-UI response whose tokens fail the client's checks (another app client or user pool, another sign-in's nonce, no single user) suggests "Sign in again. If it keeps failing, check that the configuration's user pool, app client and hosted UI domain belong together.", where it suggested `prompt: [.login]`, which cannot change what the tokens say; a user other than the one `identityExpectation` asked for still suggests it | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Hosted UI" |
| Texts: the recovery suggestion of either pool's invalid-configuration answer (`InvalidUserPoolConfigurationException`, `InvalidIdentityPoolConfigurationException`, both `.configuration`) names the user pool's settings (device tracking, for the device calls), the identity pool's settings and the client's configuration, where it named only the user pool's. `resendSignUpCode` with an empty username throws `.validation(field: "username")` saying "Username is required to resendSignUpCode", where it named `confirmSignUp`, as the plugin's does. A `resendSignUpCode` answer with no code delivery details is `.unknown` with the plugin's texts ("Unexpected error occurred with message: Unable to get Auth code delivery details"), where it had its own. The warning logged when an interrupted sign-in's record could not be deleted says that a signed-in or federated session's next restore deletes it, and that a signed-out or guest session's next restore may offer the challenge again until it is 15 minutes old, where it said the next restore deletes it | — |
| Documented, unchanged since 2.63.0: with no client for the session live in the process, `signOutStoredSession` revokes through SDK clients built from the configuration alone, so `Options.configureUserPoolClient` (a custom endpoint, a proxy, certificate pinning) is not applied to it. Hold a client for the session to sign out through it | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Signing out or purging a saved session without a client" |
