# Pending release-note items

Customer-visible changes made on `feat/amplify-cognito-client-beta` that must appear in the release notes of
whichever plugin or client release first ships them. Each entry names the change and who sees it, and links to
more detail where there is some.

## Cognito Auth plugin

| Change | Who sees it | Details |
|---|---|---|
| Keychain wipes on an access-group transition, and the access-group migration, now spare the new client's session records (`amplify.<digits>.…`), except the client default session's label item and interrupted sign-in (`amplify.1.<poolNamespace>.$default.meta` and `.challenge`). Those two belong to the plugin's session, so the access-group migration moves them with the plugin's own saved login, and the transition wipe and the migration's destination clear remove them; every other client record stays where it is. They never count as the plugin's items when it decides whether the shared service is already migrated. Migration moves one item at a time and skips a colliding item instead of stopping; an item stored in two access groups is now moved (one copy may remain in the unshared service). **Release order:** this ships in a plugin release before the client writes records, because a released plugin's access-group transition wipes the whole keychain service, the client's records included | Apps that set or change `secureStoragePreferences.accessGroup`, including apps that use `AmplifyCognitoClient`'s default session | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §6 |
| The public `KeychainStoreMigrator.migrate()` keeps its signature but skips client records, moves per item and skips collisions. It moves the client default session's two items (`$default.meta` and `$default.challenge`) like the plugin's own, and its destination clear removes them; every other client record is spared | Any external caller of that API | — |
| Rolling back from the client to the plugin with refresh-token rotation on now keeps the user signed in, for plugins from 2.51.0. The client's default session shares the plugin's saved login, so a rolled-back plugin reads the newest refresh token, including one the client rotated, and its refresh succeeds. (Before this change, which was never released, the client kept its own copy: the plugin then sent a token the client had rotated away, and the user had to sign in again.) It still happens in one case: the plugin and the client running in one process over the default session, where each keeps its tokens in memory, which is not supported. Plugins older than 2.51.0 cannot refresh at all on an app client with rotation on, whatever the client does | Apps that adopt the client and then roll back | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.8; [`issues/rollback-behaviours.md`](issues/rollback-behaviours.md) §1 |
| Signed-out sessions from non-Cognito Auth plugins now surface `AuthError.invalidState` (was `.unknown`) at the credential/token resolution sites; Face Liveness reports the `AuthError` instead of `accessDenied` | Apps with a third-party Auth plugin; Liveness SPI consumers | — |
| `AuthError.service` recovery suggestions from `FetchSessionError` and `AuthorizationError` name the engine module (`InternalAWSCognitoAuth/…`) instead of `AWSCognitoAuthPlugin/…` in their "report a bug" text | Apps that display or log recovery suggestions | — |
| Verbose log lines print engine type names (`InternalAWSCognitoAuth.Engine…`, `InternalAWSCognitoAuth.SignInMethod`) where they printed plugin type names | Anyone parsing verbose logs | — |
| The state-machine actions' log lines (252 `\(#fileID)` sites in 65 files, nearly all verbose) begin `InternalAWSCognitoAuth/<File>.swift` where they began `AWSCognitoAuthPlugin/<File>.swift`, for example `InternalAWSCognitoAuth/InitiateAuthSRP.swift Starting execution`. Category, namespace, level and the rest of each message are unchanged | Anyone filtering or parsing plugin logs by file prefix | — |
| A plugin instance is now released when nothing references it (before, every configured instance lived for the rest of the process). So a dropped or replaced second plugin instance no longer answers the Hub: one sign-in, sign-out, user deletion or expired session no longer arrives as a duplicate `signedIn`, `signedOut`, `userDeleted` or `sessionExpired` event per earlier instance. Only after an instance is released (for example `Amplify.Auth.removePlugin(for:)` while state-machine work that outlives the API call is still running), that leftover work cannot build new Cognito clients. Steps that build one with `try` (sign-in, sign-up, sign-out, delete-user and device steps) fail with the factory's `AuthError.configuration`, reported the way that step reports any client error. The session-refresh steps build theirs with `try?` and report what they report without a client: a user-pool refresh fails as invalid tokens (`AuthError.unknown`), fetching the identity ID fails with `AuthError.configuration` (`signedInIdentityIdWithNoCIDPError`), and fetching AWS credentials fails as "no identity pool" (the session returns its tokens without AWS credentials) | Apps or tests that configure more than one plugin instance in a process, or drop one while it is in use | — |
| Security: a partial sign-out no longer logs a live token. The sign-out task's info line ("Successfully completed execution for Auth.signOutAPI with result: …") printed the refresh token that could not be revoked, and the access token after a failed global sign-out, in full; it now prints them masked (`tr*****en`), as `AWSCognitoUserPoolTokens` prints its tokens. `AWSCognitoRevokeTokenError` and `AWSCognitoGlobalSignOutError` now conform to `CustomStringConvertible`, `CustomDebugStringConvertible` and `CustomReflectable`, so `print`, `debugPrint`, interpolation and `dump` mask the token too; the `refreshToken` / `accessToken` properties are unchanged | Anyone reading or collecting plugin logs; code that prints these two types | — |
| Security: two more log lines hold less. The keychain's error lines for a failed read or a failed conditional write name the record kind (`kind=deviceMetadata`, `kind=session`) instead of the keychain key, which for a device record held the username. The info line "No existing device metadata found." no longer appends the auth environment, whose description printed part of the app client secret | Anyone reading or collecting plugin logs, or matching these lines' text | — |
| Security: verbose keychain lines no longer print the keychain key. `AWSPluginsCore.KeychainStore`'s and the engine keychain's verbose lines, and `KeychainStore`'s "Unable to create Data from String" error line, name the record kind (`kind=session`, `kind=deviceMetadata`) instead, since a key can hold a username. For example, ``[KeychainStore] Started retrieving `String` from the store with kind=session`` | Anyone reading or collecting plugin logs, or matching these lines' text | — |
| Upgrading from the AWS Mobile SDK (AWSMobileClient, Amplify v1): the plugin now deletes the old keychain logins only after it has saved the migrated login. Before, it scheduled the delete before it read them, so a failed read deleted them without migrating, and the user was signed out for good (or, when only the token read failed, kept guest credentials only). A read can fail when the keychain is locked, for example during a prewarmed launch before first unlock (`errSecInteractionNotAllowed`). Now a keychain error on any read keeps every old location and migrates nothing, and the migration runs again on the next launch; a failed save keeps them too; an item that is not found is still cleared. Released plugins still have the bug | Apps upgraded from AWSMobileClient or Amplify v1 whose users have not launched since | — |
| Upgrading from the AWS Mobile SDK: old AWSMobileClient data never overwrites a newer login. When the plugin already has a saved session, it keeps it and clears the old locations without migrating them; if the plugin's own saved session cannot be read, it keeps the old locations | Apps upgraded from AWSMobileClient or Amplify v1 | — |
| Behaviour change: signing out through the plugin also clears the three AWSMobileClient keychain locations (the user pool, credentials-provider and AWSMobileClient services). So do the plugin's `deleteUser`, which signs the deleted user out, and `clearFederationToIdentityPool`. An app that still ships AWSMobileClient alongside the plugin sees that SDK's user signed out too | Apps that still ship AWSMobileClient beside the Auth plugin | — |

## AmplifyCognitoClient (new, `@_spi(AmplifyExperimental)`)

| Item | Details |
|---|---|
| Gen2 `amplify_outputs` only; Gen1 configuration is not supported. A Gen1 `amplifyconfiguration.json` (`auth.plugins`) is refused with `AuthClientError.configuration` saying it is a Gen1 configuration the client does not support, and pointing to Gen2 `amplify_outputs` | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §14.8 |
| `.default` is the Auth plugin's own saved login: it reads and writes the plugin's keychain item (`amplify.<poolNamespace>.session`, the plugin's `AmplifyCredentials` format). An app moving from the plugin to the client, or back, keeps its user, and a rolled-back plugin finds the newest login (signed out, if the user signed out through the client). One caveat: after a configuration change that copied the login, a purge (or the plugin's own sign-out) leaves the earlier configuration's copy, so rolling back to the build with that configuration signs the user in again. A sign-out through the client does not do this: it keeps the user signed out under the same configuration, and across rollbacks. The exception, as with the plugin, is a later configuration change onto an earlier configuration's copy: a change the rule does not carry deletes the signed-out login, and can land on a key that still holds the user's old copy, which then restores signed in. The label and the last user for the signed-out row are kept in a separate client item (`amplify.1.<poolNamespace>.$default.meta`). A sign-in keeps the label only for the same user, or when no one had signed in yet; a different user drops it. The plugin does not know that item: while the plugin's record holds another user, the label is hidden, and after a user is deleted through the plugin (`deleteUser`), the picker can show the deleted user as a signed-out row until the client writes the session again: a sign-in through the client, or a client refresh of another user the plugin signed in. A sign-in through the plugin doesn't replace it. There is no migration step and nothing to adopt. Named sessions keep their own records, which a plugin-only release does not see: they disappear on a rollback and come back on roll-forward. A client-only app gets no AWSMobileClient migration and no access-group migration; those are the plugin's. Plugins older than 2.51.0 cannot refresh on an app client with refresh-token rotation on, whatever the client does | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.8. Replaces the unreleased read-the-plugin's-record-at-first-load behaviour and its warning, which never shipped |
| Side by side: the plugin and the client share one saved login, but running both in one app over the default session is not supported. The plugin keeps its tokens in memory, so with refresh-token rotation on a refresh by one side can break the other's until the app relaunches. Named sessions are unaffected. When `.default` re-reads the shared saved login and finds a different user or guest from the one it holds in memory (a guest in memory replaced by a user included), for example because the plugin signed someone else in, it logs one warning naming no one, under `AmplifyCognitoClient.DefaultSession`. Logged once while the session is in memory. All handles share it; after every handle and provider is released, a new handle can log it again. It covers another user, a guest, and another guest's or federated identity's identity ID. It is never logged for a named session | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.9 |
| Amplify's category plugins (Storage, Analytics, API and the rest) do not follow `AmplifyCognitoClient` sessions, and nothing warns you. They always use the Auth plugin's session in `Amplify.Auth`, whichever client session the app is using, `.default` included. With several sessions signed in, a category call does not fail because of them: it runs as the Auth plugin's user, or as its guest, or fails if the Auth plugin has no session at all. A Storage path built from the identity ID (`StoragePath.fromIdentityID`, `.private`, `.protected`) resolves to the Auth plugin session's identity and the call succeeds there, and Analytics sends events with the Auth plugin session's AWS credentials. To make AWS calls as a particular session, pass its `credentialsProvider` to a client in the `AmplifyClients` family | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §11, limit 2; API docs on `AmplifyCognitoClient`, `credentialsProvider` and `SessionID` |
| WebAuthn: `associateWebAuthnCredential(presentationAnchor:)` requires a window (the plugin's is optional, and falls back to a window of its own). The `signIn`/`confirmSignIn` overloads without a `presentationAnchor` refuse a WebAuthn first factor, and a `WEB_AUTHN` selection with no window at all, with `.validation(field: "presentationAnchor")` before anything is sent | — |
| Hosted UI: `WebUIOptions.prefersEphemeralSession` defaults to `true` (a private browser session, no shared cookie), where the plugin's `preferPrivateSession` defaults to `false`. Pass `prefersEphemeralSession: false` for the plugin's behaviour, and sign out with `signOut(presentationAnchor:options:)` to clear the shared cookie | `WebUIOptions.swift` |
| WebAuthn: `listWebAuthnCredentials(options:)` checks `pageSize` itself (1…20, default 20) and throws `.validation(field: "pageSize")` before any request, where the plugin sends any value and reports Cognito's `InvalidParameterException` | — |
| AmplifyFoundation's `CredentialsError` (with `Disposition`/`disposition`) and `StorageUnavailableReason` are `@_spi(AmplifyExperimental)`, like the client. An app that matches `AuthSessionState.unavailable(.locked)` (or `.interrupted`, `.denied`) or `AuthClientError.storageUnavailable(.locked, …)`, or reads a provider failure's `disposition`, must import it with the SPI: `@_spi(AmplifyExperimental) import AmplifyFoundation` | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §14.8 |
| WebAuthn: associate sends one access token to `StartWebAuthnRegistration` and `CompleteWebAuthnRegistration` (the plugin fetches it again after the sheet). A token that expires while the passkey sheet is up makes `Complete` fail with `.notAuthorized`; retrying refreshes first and works | — |
| **Named sessions** (`.default` follows the plugin's rule instead: the row below). A named session is carried forward when the app's pool configuration changes, as the plugin carries its record, from the configuration the app last kept that session under (recorded per session and per app; the saved sessions themselves are shared by every app and extension in the keychain group): identity pool only → user pool added (the guest identity and its credentials are kept), user pool only → identity pool added (signed in; the identity is fetched on first use), a changed identity pool beside the same user pool (signed in, with **the user pool tokens only**: a new identity comes from the new identity pool, where the plugin keeps the old pool's identity ID), and the identity pool removed beside the same user pool (signed in, with the user pool tokens only). **Any other change carries nothing and keeps the old record**, where the plugin deletes it: an app may switch configurations at runtime under one session ID, and switching back finds that configuration's session as it was, unless it was signed out there (two configurations sharing a user pool but differing in their identity pool are one carried session: a sign-out in either ends it in both). Nothing is carried from a session whose latest saved state is signed out. **The old record is kept** after a carry, as the plugin keeps it; signing out or purging the session deletes it only if it has not been written since (an extension on the old configuration that refreshed it, or signed another user in, keeps its own), it provably holds the same user, and it is not a guest's (an extension may still use that identity). An extension that only reads the old record, without writing it, loses it at sign-out. Sign-out revokes a deleted copy's refresh token when it differs from the one it revoked and belongs to the same user pool; otherwise, and on purge, a deleted copy's refresh token is not revoked and stays valid until it expires. A rollback carries by the same rules: back to the old configuration, the kept record is used (a guest keeps its identity), unless the session, if not a guest, was signed out or purged under the new one, by this app or another. A carried session whose identity fetch fails keeps its user pool tokens and keeps waiting for its identity, as the plugin retries it; a known refusal is not retried for that user until the app restarts or the session is signed out or purged, any other failure not within 30 seconds, and until then the identity fields report that failure. A session saved by a build without this change is not carried if the configuration changes before this build first restores the session (it has no saved configuration yet). A remembered device must be remembered again: device records are not carried | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §6 |
| **The default session** follows the Auth plugin's configuration-change rule, as the plugin does with the same saved login. It copies the login on the same changes as the plugin (a user pool added to an identity-pool-only configuration; an identity pool added, changed or removed under the same user pool, app client and region), and keeps the old copy. On any other change of the saved key it deletes the old login, and `.default` starts signed out. For example, moving `.default` to another user pool signs the user out. When only the app client changes, nothing is deleted, as with the plugin: the key names the pools, not the app client, so the login stays, and its next refresh reports `sessionExpired`. A deleted login of the same user pool is revoked once, in the background, with the previous configuration's app client and endpoint; if that fails it logs "A login deleted by a configuration change could not be revoked; its refresh token stays valid until it expires." under `AmplifyCognitoClient.DefaultSession`. A login of another user pool is not revoked and stays valid until it expires. On a changed identity pool the old identity ID goes along, as with the plugin: the session keeps getting the old pool's AWS credentials while that pool exists, and gets an identity of the new pool once Cognito refuses the old one (the old pool deleted); signing out and in moves it at once. The client records the configuration in the plugin's own item, last and only after the copy or delete succeeded, so a rolled-back plugin cannot write an older login over a newer one. A keychain that cannot be read fails the restore with `storageUnavailable` and changes nothing, where the plugin treats it as "no previous configuration". A label goes with a copied login and is deleted with a deleted one. An app and its extensions sharing an access group must use the same configuration for `.default`. **For runtime switching between backends, use named sessions**, which keep each configuration's login | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §6; the beta guide, [Changing the configuration](../../AmplifyClients/AmplifyCognitoClient/README.md#changing-the-configuration) |
| `signOutStoredSession` and `purgeStoredSession` on `.default` never delete the app's login because of a configuration change. They may be called with a configuration other than the app's, so they apply the configuration rule only when it copies the login; when it would delete, they change nothing, the recorded configuration included, and the next restore under the new configuration applies the rule. When the rule copies, they still never record a configuration: only a restore records one, so the configuration the app last ran with stays recorded. `signOutStoredSession` then also signs out the login it copied from, while that still holds the user it signed out, so the user stays signed out under both configurations. `purgeStoredSession` revokes nothing and leaves that login as it was, so a later restore under the new configuration copies it again | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §6 |
| Rolling forward from the Auth plugin to the client with refresh-token rotation on, after the plugin rotated the token, resumes on the newest token: `.default` reads the plugin's own record in place, so the client refreshes with the token the plugin last saved. The dead-token rule stays for a record whose refresh token nobody can use any more: a refresh refused as a reused token fails as retryable the first time (another writer may still be saving a refresh); a second, at least 30 seconds later, with nothing saved meanwhile, reports `sessionExpired` (one `.sessionExpired` event; the session stays signed in as its user until it signs in again) | [`issues/rollback-behaviours.md`](issues/rollback-behaviours.md) §3 |
| A service response that is not JSON (such as an HTML error page from the service's edge) is `.service` with no code and the recovery suggestion to retry, not the engine's "report a bug"; the client does not retry it itself, and the app may retry it, as any temporary service failure | [`issues/sdk-non-json-response-not-retried.md`](issues/sdk-non-json-response-not-retried.md) |
| An interrupted sign-in survives the app being closed. When a sign-in stops on a challenge (an MFA or OTP code, a new password, a custom challenge, an MFA or first-factor selection, a TOTP setup), the challenge is saved in the session's device-only, never-synchronized keychain storage. The saved data is the Cognito challenge session and the step; for a TOTP setup it also includes the shared secret. The password is never saved. A client built later with the same session ID starts in `.awaitingChallenge(step)`, and the app may answer with `confirmSignIn` or start over with `signIn`. A challenge whose Cognito session has expired (three minutes by default, at most 15) fails the answer with `challengeExpired`. One saved more than 15 minutes ago (Cognito's longest challenge lifetime) is discarded on launch, and `storedSessions()` deletes such leftovers. A session whose only saved state is an interrupted sign-in is not listed by `storedSessions()`. Signing such a session out, through its client or `signOutStoredSession`, deletes its interrupted sign-in, though there is nothing to revoke. The plugin does not do this: its interrupted sign-in is lost when the app closes | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.11 |
| Sign-out takes the plugin's shape. `signOut` and `signOutStoredSession` do not throw: they return `.complete`, `.partial(revokeTokenError:globalSignOutError:hostedUIError:storageError:)` or `.failed(AuthClientError)`, with `signedOutLocally` false only for `.failed`. `.failed` leaves the user signed in: another sign-in replaced the session during the sign-out (`.invalidState`, which replaces `.superseded`), storage failed before the local sign-out, `sessionConfigurationMismatch` or another error came before anything was revoked, the user closed the hosted-UI sign-out page (`.userCancelled`), the hosted-UI sign-out page could not be shown or completed (as the plugin returns it: no hosted-UI configuration or sign-out redirect URI as `.configuration`, another sheet holding the browser as `.browserBusy`, the window gone as `.validation`, or the browser's own failure), or the task was cancelled before anything was revoked (`.unknown`, wrapping `CancellationError`). As in the plugin, a failed global sign-out skips the revoke and adds a placeholder `revokeTokenError`. A purge that fails after the local sign-out succeeded returns `.partial` with the client-only `storageError`, and `signedOutLocally` is true. Once a revoke has completed, cancellation never stops the local clear. Differences from the plugin: `.partial` carries no tokens, a federated session can be signed out, `purgeStoredSession`, and the hosted-UI sign-out page needs a window | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.7, §14.8 |
| Every client log line is under an `AmplifyCognitoClient.<area>` category (`AmplifyCognitoClient.SessionRecordStore`, `.SessionSignOut`, `.KeychainItemStore`, `.DefaultSession`), where some lines were under `SessionRecordStore` or `SessionSignOut` alone. The Cognito engine's static log sites (an unknown MFA or factor type, the passkey ceremony, the keychain store) log through the client's logger, under `AmplifyCognitoClient.MFAType`, `.AuthFactorType`, `.PlatformWebAuthnCredentials` and `.KeychainStore`, where they logged under the Auth plugin's categories once a plugin was configured. The Auth plugin's own lines are unchanged. An app that filters logs by category can match the prefix `AmplifyCognitoClient` for every client line | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §15.3 |
