# Pending release-note items

Customer-visible changes made on `feat/amplify-cognito-client-beta` that must appear in the release notes of
whichever plugin or client release first ships them. Each entry names the change and who sees it, and links to
more detail where there is some.

## Cognito Auth plugin

| Change | Who sees it | Details |
|---|---|---|
| Keychain wipes on an access-group transition, and the access-group migration, now spare the new client's session records (`amplify.<digits>.…`). Migration moves one item at a time and skips a colliding item instead of stopping; an item stored in two access groups is now moved (one copy may remain in the unshared service) | Apps that set or change `secureStoragePreferences.accessGroup` | — |
| The public `KeychainStoreMigrator.migrate()` keeps its signature but skips client records, moves per item and skips collisions | Any external caller of that API | — |
| Forward-compatible reader: when the plugin has no stored session, it reads the client's `$default` record; on sign-out it writes a signed-out marker instead of deleting when a client record exists | Apps that roll back from the client to the plugin | — |
| Rolling back to the plugin with refresh-token rotation on, after the client has rotated the refresh token: the plugin's next refresh sends the token the client rotated away, Cognito answers `RefreshTokenReuseException`, and the plugin reports `AuthError.service` wrapping it and sends no `sessionExpired` Hub event (it maps only `NotAuthorizedException` to `sessionExpired`). The session does not recover on its own; the user must sign in again | Apps that adopt the client and then roll back | [`issues/rollback-behaviours.md`](issues/rollback-behaviours.md) §1 |
| Signed-out sessions from non-Cognito Auth plugins now surface `AuthError.invalidState` (was `.unknown`) at the credential/token resolution sites; Face Liveness reports the `AuthError` instead of `accessDenied` | Apps with a third-party Auth plugin; Liveness SPI consumers | — |
| `AuthError.service` recovery suggestions from `FetchSessionError` and `AuthorizationError` name the engine module (`InternalAWSCognitoAuth/…`) instead of `AWSCognitoAuthPlugin/…` in their "report a bug" text | Apps that display or log recovery suggestions | — |
| Verbose log lines print engine type names (`InternalAWSCognitoAuth.Engine…`, `InternalAWSCognitoAuth.SignInMethod`) where they printed plugin type names | Anyone parsing verbose logs | — |
| The state-machine actions' log lines (252 `\(#fileID)` sites in 65 files, nearly all verbose) begin `InternalAWSCognitoAuth/<File>.swift` where they began `AWSCognitoAuthPlugin/<File>.swift`, for example `InternalAWSCognitoAuth/InitiateAuthSRP.swift Starting execution`. Category, namespace, level and the rest of each message are unchanged | Anyone filtering or parsing plugin logs by file prefix | — |
| A plugin instance is now released when nothing references it (before, every configured instance lived for the rest of the process). So a dropped or replaced second plugin instance no longer answers the Hub: one sign-in, sign-out, user deletion or expired session no longer arrives as a duplicate `signedIn`, `signedOut`, `userDeleted` or `sessionExpired` event per earlier instance. Only after an instance is released (for example `Amplify.Auth.removePlugin(for:)` while state-machine work that outlives the API call is still running), that leftover work cannot build new Cognito clients. Steps that build one with `try` (sign-in, sign-up, sign-out, delete-user and device steps) fail with the factory's `AuthError.configuration`, reported the way that step reports any client error. The session-refresh steps build theirs with `try?` and report what they report without a client: a user-pool refresh fails as invalid tokens (`AuthError.unknown`), fetching the identity ID fails with `AuthError.configuration` (`signedInIdentityIdWithNoCIDPError`), and fetching AWS credentials fails as "no identity pool" (the session returns its tokens without AWS credentials) | Apps or tests that configure more than one plugin instance in a process, or drop one while it is in use | — |
| Security: a partial sign-out no longer logs a live token. The sign-out task's info line ("Successfully completed execution for Auth.signOutAPI with result: …") printed the refresh token that could not be revoked, and the access token after a failed global sign-out, in full; it now prints them masked (`tr*****en`), as `AWSCognitoUserPoolTokens` prints its tokens. `AWSCognitoRevokeTokenError` and `AWSCognitoGlobalSignOutError` now conform to `CustomStringConvertible`, `CustomDebugStringConvertible` and `CustomReflectable`, so `print`, `debugPrint`, interpolation and `dump` mask the token too; the `refreshToken` / `accessToken` properties are unchanged | Anyone reading or collecting plugin logs; code that prints these two types | — |
| Security: two more log lines hold less. The keychain's error lines for a failed read or a failed conditional write name the record kind (`kind=deviceMetadata`, `kind=session`) instead of the keychain key, which for a device record held the username. The info line "No existing device metadata found." no longer appends the auth environment, whose description printed part of the app client secret | Anyone reading or collecting plugin logs, or matching these lines' text | — |

## AmplifyCognitoClient (new, `@_spi(AmplifyExperimental)`)

| Item | Details |
|---|---|
| Gen2 `amplify_outputs` only; Gen1 configuration is not supported. A Gen1 `amplifyconfiguration.json` (`auth.plugins`) is refused with `AuthClientError.configuration` saying it is a Gen1 configuration the client does not support, and pointing to Gen2 `amplify_outputs` | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §14.8 |
| Running the plugin and the client side by side over the same default session is not supported; `.default` adopts the plugin's record at first load only. After adoption `.default` and the plugin share one refresh token (the plugin's, copied byte for byte; rotation is off), so signing out through `Amplify.Auth`, or any other revocation of that token, invalidates `.default` server-side; `.default` keeps reporting `.signedIn` until its next refresh fails. When `.default` restores its own signed-in record while the plugin's record holds a different signed-in principal, it logs one warning each time the default session is first loaded (a new client instance logs again), under the `AmplifyCognitoClient` category, naming no one: "The Auth plugin holds a different session than this client's default session; running both over the default session is not supported." Warns on another `sub` (else user name), on a plugin user beside a client guest or federated record, and on two guests with different identity IDs. Silent when either side is signed out or absent, on the same user, on a plugin guest beside a client user (the plugin signed out; it is not another user), and when the plugin's record cannot be read or described. The check reads the plugin's record once, read-only, after the restore and outside it, so it never delays or fails the restore | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.9 |
| Amplify's category plugins (Storage, Analytics, API and the rest) do not follow `AmplifyCognitoClient` sessions, and nothing warns you. They always use the Auth plugin's session in `Amplify.Auth`, whichever client session the app is using, `.default` included. With several sessions signed in, a category call does not fail because of them: it runs as the Auth plugin's user, or as its guest, or fails if the Auth plugin has no session at all. A Storage path built from the identity ID (`StoragePath.fromIdentityID`, `.private`, `.protected`) resolves to the Auth plugin session's identity and the call succeeds there, and Analytics sends events with the Auth plugin session's AWS credentials. To make AWS calls as a particular session, pass its `credentialsProvider` to a client in the `AmplifyClients` family | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §11, limit 2; API docs on `AmplifyCognitoClient`, `credentialsProvider` and `SessionID` |
| WebAuthn: `associateWebAuthnCredential(presentationAnchor:)` requires a window (the plugin's is optional, and falls back to a window of its own). The `signIn`/`confirmSignIn` overloads without a `presentationAnchor` refuse a WebAuthn first factor, and a `WEB_AUTHN` selection with no window at all, with `.validation(field: "presentationAnchor")` before anything is sent | — |
| Hosted UI: `WebUIOptions.prefersEphemeralSession` defaults to `true` (a private browser session, no shared cookie), where the plugin's `preferPrivateSession` defaults to `false`. Pass `prefersEphemeralSession: false` for the plugin's behaviour, and sign out with `signOut(presentationAnchor:options:)` to clear the shared cookie | `WebUIOptions.swift` |
| WebAuthn: `listWebAuthnCredentials(options:)` checks `pageSize` itself (1…20, default 20) and throws `.validation(field: "pageSize")` before any request, where the plugin sends any value and reports Cognito's `InvalidParameterException` | — |
| AmplifyFoundation's `CredentialsError` (with `Disposition`/`disposition`) and `StorageUnavailableReason` are `@_spi(AmplifyExperimental)`, like the client. An app that matches `AuthSessionState.unavailable(.locked)` (or `.interrupted`, `.denied`) or `AuthClientError.storageUnavailable(.locked, …)`, or reads a provider failure's `disposition`, must import it with the SPI: `@_spi(AmplifyExperimental) import AmplifyFoundation` | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §14.8 |
| WebAuthn: associate sends one access token to `StartWebAuthnRegistration` and `CompleteWebAuthnRegistration` (the plugin fetches it again after the sheet). A token that expires while the passkey sheet is up makes `Complete` fail with `.notAuthorized`; retrying refreshes first and works | — |
| A session is carried forward when the app's pool configuration changes, as the plugin carries its record, from the configuration the app last kept that session under (recorded per session and per app; the saved sessions themselves are shared by every app and extension in the keychain group): identity pool only → user pool added (the guest identity and its credentials are kept), user pool only → identity pool added (signed in; the identity is fetched on first use), a changed identity pool beside the same user pool (signed in, with **the user pool tokens only**: a new identity comes from the new identity pool, where the plugin keeps the old pool's identity ID), and the identity pool removed beside the same user pool (signed in, with the user pool tokens only). **Any other change carries nothing and keeps the old record**, where the plugin deletes it: an app may switch configurations at runtime under one session ID, and switching back finds that configuration's session as it was, unless it was signed out there (two configurations sharing a user pool but differing in their identity pool are one carried session: a sign-out in either ends it in both). Nothing is carried from a session whose latest saved state is signed out. **The old record is kept** after a carry, as the plugin keeps it; signing out or purging the session deletes it only if it has not been written since (an extension on the old configuration that refreshed it, or signed another user in, keeps its own), it provably holds the same user, and it is not a guest's (an extension may still use that identity). An extension that only reads the old record, without writing it, loses it at sign-out. Sign-out revokes a deleted copy's refresh token when it differs from the one it revoked and belongs to the same user pool; otherwise, and on purge, a deleted copy's refresh token is not revoked and stays valid until it expires. A rollback carries by the same rules: back to the old configuration, the kept record is used (a guest keeps its identity), unless the session, if not a guest, was signed out or purged under the new one, by this app or another. A carried session whose identity fetch fails keeps its user pool tokens and keeps waiting for its identity, as the plugin retries it; a known refusal is not retried for that user until the app restarts or the session is signed out or purged, any other failure not within 30 seconds, and until then the identity fields report that failure. A session saved by a build without this change is not carried if the configuration changes before this build first restores the session (it has no saved configuration yet); nor is `.default` taken over from the plugin in that release. A remembered device must be remembered again: device records are not carried | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §6 |
| Rolling forward from the Auth plugin with refresh-token rotation on, after the plugin rotated the token: `.default` resumes on its own older record, and its refresh token is dead. The first refresh fails as retryable (another writer may still be saving a refresh); a second, at least 30 seconds later, with nothing saved meanwhile, reports `sessionExpired` (one `.sessionExpired` event; the session stays signed in as its user until it signs in again) | [`issues/rollback-behaviours.md`](issues/rollback-behaviours.md) §3 |
| A service response that is not JSON (such as an HTML error page from the service's edge) is `.service` with no code and the recovery suggestion to retry, not the engine's "report a bug"; the client does not retry it itself, and the app may retry it, as any temporary service failure | [`issues/sdk-non-json-response-not-retried.md`](issues/sdk-non-json-response-not-retried.md) |
| An interrupted sign-in survives the app being closed. When a sign-in stops on a challenge (an MFA or OTP code, a new password, a custom challenge, an MFA or first-factor selection, a TOTP setup), the challenge is saved in the session's device-only, never-synchronized keychain storage. The saved data is the Cognito challenge session and the step; for a TOTP setup it also includes the shared secret. The password is never saved. A client built later with the same session ID starts in `.awaitingChallenge(step)`, and the app may answer with `confirmSignIn` or start over with `signIn`. A challenge whose Cognito session has expired fails the answer with `challengeExpired`. One saved more than 15 minutes ago (Cognito's longest challenge lifetime) is discarded on launch, and `storedSessions()` deletes such leftovers. A session whose only saved state is an interrupted sign-in is not listed by `storedSessions()`. The plugin does not do this: its interrupted sign-in is lost when the app closes | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.11 |
