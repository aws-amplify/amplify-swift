## AmplifyKinesisClient and AmplifyFirehoseClient

| Change | Details |
|---|---|
| New, additive: `Options.cacheIdentifier` names a client's offline cache within its region. By default (`nil`) every client of a region shares one cache file, as before, so existing caches are kept; clients given two sessions' credentials then share it, and one session's flush sends the other's records with its own credentials. With an identifier (an `AmplifyCognitoClient` session's `sessionId.stringValue`, say) the client uses a cache of its own. An empty identifier throws `KinesisError.validation` / `FirehoseError.validation` from the initializer. The identifier is fixed when the client is created: flush before creating a client with another identifier, or with one for the first time, since records already cached stay where they are. A cache outlives its session's sign-out: its records stay until a client with that identifier flushes or clears them, or its flush finds the session signed out and discards them, and the emptied file is never removed. Calls that build `Options` compile and behave as before; code that passes `Options.init` as a function value must add the parameter, or call it in a closure | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Credentials for other AmplifyClients" |
| Behaviour change: a flush whose credentials provider throws AmplifyFoundation's `CredentialsError` (an `AmplifyCognitoClient` session's provider does) throws the new `KinesisError.credentials` / `FirehoseError.credentials`, with the provider's description, recovery suggestion and error, where it threw `.unknown`. Code that switches over `KinesisError` or `FirehoseError` needs the new case, or `@unknown default`. Any other provider error is unchanged: `.unknown`, and a retry counted. The flush stops at the stream it was sending and counts no retry against the records left in the cache, where each such flush used to count one and `maxRetries` of them deleted the records, so an expired session's queued records were lost before the user could sign in again. The records follow the error's `disposition`: `.discard` (signed out) removes the records cached when the flush began, only for a client with a `cacheIdentifier`, since the region's shared cache holds every session's records; `.retryAfterReauthentication`, `.retryWithBackoff` and `.failLoudly` keep them for a later flush. Records kept this way no longer expire through `maxRetries`, so the cache can fill to `cacheMaxBytes`, after which `record` throws `cacheLimitExceeded` | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Credentials for other AmplifyClients" |
| The automatic flush backs off while the credentials provider keeps throwing `CredentialsError` (an `AmplifyCognitoClient` session's does): its interval doubles with each failed flush, up to 15 minutes, until a flush completes. A wait already under way is not shortened: call `enable()` once the session can vend credentials again to restart the schedule. A provider's other errors, and send failures, still retry at the configured interval, so an app whose own provider throws no `CredentialsError` sees no change | — |
| Logs: an automatic flush that fails on a `CredentialsError` whose `disposition` is `.failLoudly` (a misconfiguration, which no retry fixes) logs at error, "Auto-flush failed: the credentials provider cannot vend credentials", where it logged the warning "Auto-flush failed"; every other failed automatic flush still logs that warning. A flush that discards records (`.discard`, for a client with a `cacheIdentifier`) logs the warning "Discarded the records cached before the flush: …", ending with the provider's description | — |
| A cancelled flush counts no retry against the cached records | — |
| The initializers throw `KinesisError` / `FirehoseError` when the offline cache can't be opened (`.cache`), where they threw an internal error type that app code could not name | — |

## AmplifyCognitoClient (`@_spi(AmplifyExperimental)`, beta)

| Change | Details |
|---|---|
| Breaking for SPI-beta apps: every public type whose name began `AuthClient` now begins `AmplifyCognitoClient`, the prefix the client itself and its `AmplifyCognitoClientUserPoolConfigurationProvider` already had: `AuthClientConfiguration` is `AmplifyCognitoClientConfiguration`, `AuthClientError` is `AmplifyCognitoClientError`, `AuthClientUser` is `AmplifyCognitoClientUser`, and so on for the options, results, steps, errors and model types. Two also gain `Auth`, after the call they belong to: `AuthClientSession` is `AmplifyCognitoClientAuthSession` and `AuthClientFetchSessionOptions` is `AmplifyCognitoClientFetchAuthSessionOptions`, so that `fetchAuthSession`'s result does not read as the session whose ID, state and kind other types name. Nothing but the names changes, and text that spells a type name spells the new one: error descriptions (`AmplifyCognitoClientServiceErrorCode.<case>: …`), recovery suggestions, the redacted `description` of the token and credential types, and the bridged `NSError` domain. Nothing saved on a device depends on the names. The eight types that had no prefix take it too: `SessionID` is `AmplifyCognitoClientSessionID`, `StoredSession` is `AmplifyCognitoClientStoredSession`, `SessionKind` is `AmplifyCognitoClientSessionKind`, `AuthSessionState` is `AmplifyCognitoClientSessionState`, `AuthEvent` is `AmplifyCognitoClientEvent`, `WebUIOptions` is `AmplifyCognitoClientWebUIOptions`, `CognitoCredentialsProvider` is `AmplifyCognitoClientCredentialsProvider` and `CognitoUserPoolTokenProvider` is `AmplifyCognitoClientUserPoolTokenProvider`. The module and its class share a name, so an app could not write `AmplifyCognitoClient.SessionID` to tell one of them from a type of its own. To move, in this order and as whole type names: rename the eight; replace `AuthClient` with `AmplifyCognitoClient` wherever it starts a type name; then rename `AmplifyCognitoClientSession` and `AmplifyCognitoClientFetchSessionOptions` to the two names above. The other rows of this table use the new names | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) |
| Breaking for SPI-beta apps: `AmplifyCognitoClientStoredSession` has `state: AmplifyCognitoClientSessionState` beside `kind`, and `AmplifyCognitoClientStoredSession.init` takes `state:`. It is the state a client built with the row's `sessionId` restores to (`currentSessionState()`), read from what is saved with no network call and no client (two exceptions, where a restore changes what is saved, are in the README's listing notes): `.signedIn(user)` (with or without AWS credentials, and also for a session whose refresh token a refresh already proved dead, as its client reports it), `.guest`, `.federated(identityId:)`, `.signedOut`, `.awaitingChallenge(step)` or `.failed`; never `.unavailable`, since a locked keychain still throws `storageUnavailable`. Behaviour changes, in what `storedSessions` lists: a sign-in that stopped on a challenge is now listed as `.awaitingChallenge(step)` while it can still be resumed, with or without `includingSignedOut`, both over a signed-out or guest row (a signed-out row was hidden by the default listing; the row keeps its `kind`, label and last user) and for a session with nothing else saved, such as a first sign-in interrupted at MFA (not listed before; its row has no label or user and `kind == .signedOut`); and a saved record this version cannot read (saved by a newer version of the app, or damaged) is now a `.failed` row with no label or user and `kind == .userPoolOnly` (left out before); a readable record that does not itself name its user (saved before records kept the user's ID, or federated) and whose credentials cannot be read, or name no user or identity, is `.failed` too, with its label and `kind` as saved. `includingSignedOut: false` now hides the rows whose `state` is `.signedOut`. `kind` is unchanged for every row listed before. Code that treats every listed row as a usable session should switch over `row.state`; to resume an `.awaitingChallenge` row, build a client with its `sessionId` and call `confirmSignIn`. To tell, `storedSessions` now reads the interrupted sign-in saved for a signed-out or guest row, or for a session with nothing else saved, and throws `storageUnavailable` when it cannot read it | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Listing saved sessions" |
| A sign-out no longer leaves credentials in a saved record that is signed out and yet holds some, a shape no version writes. `signOut()`, `signOutWithWebUI` and `signOutStoredSession` sign such a named session out as they do a login: the credentials are revoked and the row cleared, keeping its label and last user, and a live client sends `.signedOut`. Where the credentials cannot be read the result is `.partial` with a `revokeTokenError`, as for a login whose credentials cannot be read. Before, these calls returned `.complete` and left the credentials saved, unless the call also purged the row. `.default` is not affected: over the Auth plugin's guest or federated login, under a configuration with no identity pool, it is listed signed out, and a sign-out there still returns `.complete` and revokes nothing | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) |
| Breaking for SPI-beta apps: `AmplifyCognitoClientStoredSession.username: String?` is replaced by `user: AmplifyCognitoClientUser?`, and `AmplifyCognitoClientStoredSession.init` takes `user:` in its place. `user` is the signed-in user, or a signed-out row's last user: the same value as `getCurrentUser()` and `AmplifyCognitoClientSessionState.signedIn(_:)`, so `user.userId` matches a picker row to a live client, or to another row of the same person. It is `nil` for guest and federated rows. It is also `nil` where the saved row keeps a username and no user ID (rows saved before rows kept one), unless that row is signed in and its saved credentials still name the user, which the listing reads offline; such a row had a `username` before. `user.username` is the value `username` held: Cognito's username, often a UUID or `<Provider>_<id>`, not a display name, so title rows with `label`. Replace `row.username` with `row.user?.username` | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Listing saved sessions" |
| New, additive: `AmplifyCognitoClientSessionID.named(_:label:)` and `AmplifyCognitoClientSessionID.new(label:)` take an optional picker label, readable as `AmplifyCognitoClientSessionID.label`, for an app that knows the label when it adds an account. A sign-in through a client built with that ID (hosted UI included), a federation or a guest saves it as the row's label when the row keeps none, so no `setSessionLabel` call is needed; building the client still saves nothing. A label the row keeps wins (the same user's, or one set before anyone signed in); when a different user signs in, the previous user's label is dropped as before and the ID's label is saved for the new user. `setSessionLabel`, instance and static, replaces it; once it clears the label with `nil`, the next sign-in through an ID created with a label saves that label again, and a refresh never does. The label is not part of the ID: `==`, hashing and `Codable` use `stringValue` only, so saved IDs are unchanged, two IDs that differ only in label are one session (which uses the label of the client that built it), and `.default` has none (`named("$default", label:)` is `.default` with one). Calls without a label compile and behave as before; code that passes `AmplifyCognitoClientSessionID.named` or `AmplifyCognitoClientSessionID.new` as a function value must now call it in a closure | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Labels" |
| New, additive: a static `setSessionLabel(_:sessionId:configuration:accessGroup:)` labels any saved session without building a client for it, for an account picker. It goes through the session's client when one is live in the process, and otherwise writes the saved row itself (for `.default`, the label kept beside the plugin's record), after carrying forward a session saved under a previous configuration as its next restore would. A session with nothing saved gets a labelled signed-out row. The instance `setSessionLabel(_:)` is unchanged | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Labels" |
| New, additive: the static `signOutStoredSession(sessionId:configuration:accessGroup:options:)` takes `AmplifyCognitoClientSignOutOptions`, defaulted, as `signOut(options:)` does. `globalSignOut` signs the user out of every device and `purgeStoredSession` removes the row once the session is signed out, with or without a client for the session live in the process; a purge that fails after the sign-out is `.partial` with a `storageError`. A call without `options:` behaves as before | [README](../../AmplifyClients/AmplifyCognitoClient/README.md) "Signing out or purging a saved session without a client" |
| Breaking for SPI-beta apps: every field of the `AmplifyCognitoClient…Options` types, of `AmplifyCognitoClientWebUIOptions` and of `AmplifyCognitoClient.Options` (`sessionId`, `accessGroup`, `configureUserPoolClient`) is `let`, not `var`, as the released clients' `Options` are. | Breaking for SPI-beta apps: `AmplifyCognitoClient.init(from:bundle:options:)` is removed, `AmplifyCognitoClient()` with it. It only forwarded to `AmplifyCognitoClientConfiguration(from:bundle:)`. | Behaviour change: an expired session whose user signs in again keeps answering `sessionExpired` (`.retryAfterReauthentication`) from `credentialsProvider` and `userPoolTokenProvider` while that sign-in waits on a challenge, where 2.64.0 answered `notSignedIn` (`.discard`). They are then sent as whoever signed in, the expired user or another, so clear the client's cache first if another user may sign in to the session. | Breaking for SPI-beta apps: `fetchAuthSession` throws instead of reporting failures in its fields, and `AmplifyCognitoClientAuthSession`'s four `…Result` fields are plain optionals: `identityId`, `awsCredentials`, `userSub` and `userPoolTokens`, with an `init` whose parameters all default to `nil`. A fetch whose refresh finds the session signed out by another process now answers as a signed-out session's fetch does, becoming a guest where the identity pool allows one.
