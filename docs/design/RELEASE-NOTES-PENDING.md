whichever plugin or client release first ships them. Each entry names the change and who sees it, and links to
more detail where there is some.

| Keychain wipes on an access-group transition, and the access-group migration, now spare the new client's session records (`amplify.<digits>.…`), except the client default session's label item and interrupted sign-in (`amplify.1.<poolNamespace>.$default.meta` and `.challenge`). Those two belong to the plugin's session, so the access-group migration moves them with the plugin's own saved login, and the transition wipe and the migration's destination clear remove them; every other client record stays where it is. They never count as the plugin's items when it decides whether the shared service is already migrated. ## AmplifyCognitoClient (new, `@_spi(AmplifyExperimental)`)

| Item | Details |
|---|---|
| Gen2 `amplify_outputs` only; Gen1 configuration is not supported. A Gen1 `amplifyconfiguration.json` (`auth.plugins`) is refused with `AuthClientError.configuration` saying it is a Gen1 configuration the client does not support, and pointing to Gen2 `amplify_outputs` | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §14.8 |
| `.default` is the Auth plugin's own saved login: it reads and writes the plugin's keychain item (`amplify.<poolNamespace>.session`, the plugin's `AmplifyCredentials` format). An app moving from the plugin to the client, or back, keeps its user, and a rolled-back plugin finds the newest login (signed out, if the user signed out through the client). One caveat: after a configuration change that copied the login, a purge (or the plugin's own sign-out) leaves the earlier configuration's copy, so rolling back to the build with that configuration signs the user in again. A sign-out through the client does not do this: it keeps the user signed out under the same configuration, and across rollbacks; it also clears the AWSMobileClient (Amplify v1) logins a released plugin would migrate over it, best effort (the AWSMobileClient row below). The exception, as with the plugin, is a later configuration change onto an earlier configuration's copy: a change the rule does not carry deletes the signed-out login, and can land on a key that still holds the user's old copy, which then restores signed in. The label and the last user for the signed-out row are kept in a separate client item (`amplify.1.<poolNamespace>.$default.meta`). A sign-in keeps the label only for the same user, or when no one had signed in yet; a different user drops it. The plugin does not know that item: while the plugin's record holds another user, the label is hidden, and after a user is deleted through the plugin (`deleteUser`), the picker can show the deleted user as a signed-out row until the client writes the session again: a sign-in through the client, a client refresh of another user the plugin signed in, a guest fetch or a purge. A sign-in through the plugin doesn't replace it. That row goes away when the plugin starts using the client internally. The same row can follow a rollback to a released plugin built with another configuration, across a change its rule does not carry: that plugin deletes the login but not the label item, which this release's plugin removes with it. There is no migration step and nothing to adopt. Named sessions keep their own records, which a plugin-only release does not see: they disappear on a rollback and come back on roll-forward, unless the rolled-back release wiped its keychain service (an access-group transition, or the first configuration of a release before 2.53.3: the rollback rows below). A client-only app gets no AWSMobileClient migration and no access-group migration; those are the plugin's | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.8. Replaces the unreleased read-the-plugin's-record-at-first-load behaviour and its warning, which never shipped |
| Rolling back from the client to the Auth plugin with refresh-token rotation on keeps the user signed in, on plugin releases from 2.53.3 (and on 2.51.0 to 2.53.2 where that release does not wipe the keychain service when it first configures: the next row). `.default` is the plugin's saved login, so a rolled-back plugin reads the newest refresh token, including one the client rotated, and its refresh succeeds. The one exception is the plugin and the client running in one process over the default session, where each keeps its tokens in memory, which is unsupported until the plugin uses the client internally. Plugins older than 2.51.0 cannot refresh at all on an app client with rotation on, whatever the client does | [Design](AGREED-DESIGN-AmplifyCognitoClient.md) §4.8; [`issues/rollback-behaviours.md`](issues/rollback-behaviours.md) §1 |

| **Named sessions** (`.default` follows the plugin's rule instead: the row below). A named session is carried forward when the app's pool configuration changes, as the plugin carries its record, from the configuration the app last kept that session under (recorded per session and per app; the saved sessions themselves are shared by every app and extension in the keychain group): identity pool only → user pool added (the guest identity and its credentials are kept), user pool only → identity pool added (signed in; the identity is fetched on first use), a changed identity pool beside the same user pool (signed in, with **the user pool tokens only**: a new identity comes from the new identity pool, where the plugin keeps the old pool's identity ID), and the identity pool removed beside the same user pool (signed in, with the user pool tokens only).
